# Checkout, оплата и исполнение

## Минимальная серверная последовательность

```text
1. Клиент отправляет ID строк и fulfillment context.
2. Сервер проверяет доступность, ограничения, цены и скидки.
3. Сервер создаёт короткоживущий PriceQuote.
4. Сервер резервирует остаток/слот, если модель это требует.
5. Сервер создаёт pending Order/Booking и платёжную сессию с idempotency key.
6. Платёжный провайдер обрабатывает оплату.
7. Подписанный webhook меняет статус оплаты идемпотентно.
8. Backend запускает исполнение и уведомления.
9. Confirmation page читает серверный статус, а не доверяет query string.
10. Истёкшая сессия освобождает резерв.
```

Stripe документирует аналогичный lifecycle Checkout: сессия создаётся приложением, после оплаты заказ исполняется по `checkout.session.completed`, а `checkout.session.expired` может возвращать ограниченный товар в доступность. Это паттерн, а не требование использовать Stripe: конкретный провайдер выбирается по рынку.

Источник: https://docs.stripe.com/payments/checkout/how-checkout-works

## Идемпотентность

- один пользовательский submit получает стабильный ключ попытки;
- повторный клик, retry сети и повтор webhook не создают второй заказ;
- обработчик webhook сначала проверяет подпись и уже обработанный event ID;
- переходы статуса валидируются: старое событие не откатывает новый статус;
- внешние side effects — чек, письмо, POS ticket — имеют собственный ключ дедупликации.

## Цена

Перед оплатой сервер возвращает:

```json
{
  "currency": "RUB",
  "subtotalMinor": 240000,
  "discountsMinor": 20000,
  "deliveryMinor": 19900,
  "taxMinor": 0,
  "feesMinor": 0,
  "totalMinor": 239900,
  "expiresAt": "2026-08-18T18:30:00+03:00"
}
```

Имена полей адаптируются к backend. Инвариант: пользователь видит тот же состав цены, который подтверждает сервер. После истечения quote выполняется repricing с явным diff.

## Гостевая покупка

Аккаунт предлагается после или рядом с подтверждением, если он не нужен для регулируемой идентификации. Сохранение данных и маркетинговая подписка не объединяются с обязательным согласием на исполнение заказа.

Исследование checkout Baymard отмечает гостевой checkout и сокращение лишнего ввода как важные меры снижения трения; W3C рекомендует спрашивать только данные, необходимые для транзакции.

Источники:

- https://baymard.com/learn/checkout-flow-ux-optimization
- https://www.w3.org/WAI/tutorials/forms/

## Платёжные состояния UI

| Backend | UI | Разрешённое действие |
| --- | --- | --- |
| `pending` | Платёж обрабатывается | обновить статус, не платить повторно автоматически |
| `requires_action` | Нужен дополнительный шаг | продолжить безопасный flow провайдера |
| `paid` | Оплата подтверждена | показать исполнение/заказ |
| `failed` | Оплата не прошла + причина, если безопасно | повторить или сменить способ |
| `canceled` | Попытка отменена | вернуться к проверенному заказу |
| `refund_pending` | Возврат начат | показать сумму и ожидаемый срок |
| `refunded` | Возврат подтверждён | показать итог и канал поддержки |

## Доставка и самовывоз

Контекст включает адрес/геокод, locationId, способ, выбранное окно, ETA, стоимость, минимум заказа и ограничения. Смена контекста повторно валидирует все строки.

Для еды различать:

- ресторан открыт для просмотра, но уже не принимает заказ на выбранное время;
- блюдо существует глобально, но недоступно в точке;
- кухня приняла заказ;
- курьер назначен;
- ETA изменился после принятия.

## Запись

Slot hold должен иметь `expiresAt`. После истечения checkout не создаёт скрытую запись на другое время. При оплате депозита booking подтверждается только после согласованного сочетания webhook + availability transaction.

## Подтверждения и чеки

Уведомление не заменяет сохранённый статус заказа. Email/SMS/мессенджер — каналы доставки копии. При недоставке уведомления заказ остаётся доступен по безопасной ссылке или в аккаунте.

Для российского запуска отдельно проверить актуальные требования 54-ФЗ и фискализации у выбранного провайдера/ОФД. ФНС указывает обязанность формировать и направлять чек при расчётах и отдельно разъясняет особенности интернет-расчётов.
